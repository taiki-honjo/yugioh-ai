## 1. ユーザーの目的と、決まった方針

個人所有のPCで、遊戯王をプレイする専用AIを学習・改善したい。

「好きなデッキを扱うこと」「対戦の強さ」「自分のPCで学習・改善できること」のうち、ユーザーが最優先に選んだのは **自分のPCで学習・改善できること**。

最初は公開モデルの試用を考えていたが、この優先順位を受けて、ygo-agentの既存の学習実装と対応済みデッキを使う小規模なローカル学習を実施した。ユーザーは「まずやってみて」と指示し、Windowsの再起動とUbuntuのアカウント作成を自身で行った。

初回試行で使ったデッキは、既存の学習例に同梱された青眼（ブルーアイズ）。ユーザーが将来も青眼だけを使うと決めたわけではない。

現段階の到達点は **対戦・GPU学習・保存・読み込み・重みを引き継いだ追加学習が、このPCで動いたこと**。強さの向上や、現代の全デッキへの対応は実証していない。

## 2. AI・LLM・Jevの役割についての検討

基本構成は次の役割分担で考えている。

| 部品 | 役割 |
| --- | --- |
| ルールエンジン | カード効果、召喚、チェーン、合法な選択肢、勝敗を処理する |
| 観測・行動の変換 | プレイヤーに見える情報を入力にし、モデルの選択をエンジンの操作に戻す |
| ローカルの専用モデル | 次の行動を選ぶ。今回、実際に学習で重みを更新した対象 |
| 学習・評価プログラム | 自己対戦の経験を集めて更新し、保存・比較する |
| LLM | 設計、実装、ログ分析、改善案の支援 |
| Jev | 今後、学習を助ける判断役として検討する候補 |

ユーザーの言う「jev」は **TypeSafe AIのJev** と確認済み。参照先：https://typesafe.ai/

会話時に公式資料を調べ、状況と質問に対して選択肢・スコア・確率などを返すAPIとして検討した。組み合わせ案は以下。

1. エンジンが示した合法手から、Jevが直接行動を選ぶ。
2. 専用モデルの候補をJevが評価する。
3. Jevの判断を参考データとして、ローカル専用モデルの学習を助ける。

ローカルで学習・改善するという目的に合わせ、3を将来の候補としている。ただし、Jevが遊戯王で良い教師になるか、専用モデルの学習を改善するかは未検証。まず既知の局面や対戦で判断の質を評価する必要がある。

**今回の対戦・学習でJev APIは利用していない。Jev自身の重みの学習も行っていない。対戦中に毎手LLM APIを呼ぶ構成でもない。** Jevの確率を、そのままその行動の勝率と解釈しない。

学習済みモデルとは、学習で調整された数値である「重み」と、その構造・設定の組み合わせ。対戦ログを保存しただけではモデルは更新されない。Jevの回答を集める場合も、別途それを学習に取り込む処理が必要になる。

## 4. 実行した検証と、その意味

今回は、公開済みの強いモデルを読み込んで始めた実験ではなく、既存のygo-agentコードを用いて初期化したモデルを青眼の自己対戦で短く学習させた。

| 検証 | 実行結果 |
| --- | --- |
| GPU基礎確認 | Ubuntu内でRTX 4060 Tiを認識し、JAXのGPU行列計算に成功 |
| エンジン確認 | 青眼のランダム行動同士で4戦を完走、正常終了 |
| 学習 | 4並列、4,096判断分、32更新のGPU学習を正常終了 |
| 保存・読み込み | 保存モデルを別プロセスで読み込んで4戦完走 |
| 簡単な対戦評価 | ランダム相手に2勝2敗、評価seed=100 |
| 追加学習 | 4,096判断分の学習後の重みを読み込み、512判断分・4更新を追加して保存 |
| 重みの検証 | 追加学習で3,248,221個のパラメータ値が変化。最終パラメータはすべて有限値 |

「4,096判断」は4,096対戦や4,096ターンではない。召喚、効果、対象など、モデルが選択する細かい意思決定を数えたもの。学習データを集める側は先読みのため余分な判断を進める場合があり、ログの収集数と更新に使用した数が同じとは限らない。

4戦の2勝2敗は、動作確認の結果。安定した勝率や強さの向上を示す統計的な評価ではない。自己対戦の勝率や重みの変化だけでも、強くなったとは判断できない。

### 実測値

| 実行 | 経過時間 | GPU全体メモリ使用量の最大 |
| --- | ---: | ---: |
| 最初の4,096判断分の学習 | 98.093秒 | 5210 MiB |
| 保存不具合の修正後、4,096判断分を再実行 | 51.989秒 | 2907 MiB |
| 512判断分の追加学習 | 42.313秒 | 2740 MiB |

時間にはPython起動・初期化・コンパイル・内部評価を含む。再実行時にはコンパイルキャッシュが存在していたため、単純な速度比較や長時間学習への比例換算はしない。GPU値にはWindowsや他のアプリの使用分も含む。修正後の学習で記録したLinux子プロセス最大RSSは約1900 MiBであり、PC全体のRAM使用量ではない。

最初の実行では学習は正常終了したが、保存不具合でモデルファイルが残らなかった。現在配布しているモデルは、修正後の成功した実行から保存したもの。

### 「追加学習」と「完全な再開」の違い

`--checkpoint` はモデルの重みなどを読み込む一方で、最適化の内部状態を新しく初期化する。乱数状態、学習カウンター、対戦途中の状態も完全には復元しない。

したがって、今回確認したのは **学習済みの重みを引き継いだ追加学習**。中断した時点の学習状態を丸ごと復元する完全な再開は未実装。

追加学習後のモデルはメッセージパックの復元・構造・形状・全パラメータの有限性を確認した。別プロセスで4戦評価した対象は、その前の4,096判断分のモデル。追加学習後のモデルの対戦成績は未測定。

## 5. 遭遇した問題と修正

### Windows改行のデッキ読み込み

Windowsで取得したデッキをLinuxにコピーしたところ、CRLF改行をネイティブ側が読み取れず「メインデッキ0枚」と判定した。初期コピーではデッキとカード番号リストの改行をLFに正規化した。最終的に採用した固定版はZIPからLinux上へ展開したもの。

### 配布済みエンジンと新しいソース・データの不整合

最初に取得したmainのコミットは `dbf5142d49aab2e6beb4150788d4fffec39ae3e5`。この版とカードデータを、2024年7月8日更新の配布済みエンジンと組み合わせると、`announce_card`（カード名を選ぶ処理）付近で停止した。

最終的には前述の2024年7月のソース・スクリプト・DBへ揃えて動作した。最初のmain側のデッキには後から追加されたカードもあったため、デッキを説明する際には最終採用版を参照する。

### 小規模学習の保存ファイルが消える不具合

元実装は保存名を百万判断単位に丸めるため、小さい実行では同じファイル名が繰り返された。さらに、古い保存物を消す処理が、同じ名前の最新ファイルを削除していた。

修正内容：

- `scripts/cleanba.py`：保存名を実際の判断数による名前に変更。
- `ygoai/rl/ckpt.py`：保持リストに同一パスを重複登録しないよう変更。
- `scripts/cleanba.py`：ウォームアップ後に時間基準をリセットする際、評価時間の累積値もリセットし、負のSPS表示を修正。

同名での繰り返し保存・保持件数の回帰確認と、修正後の実際の学習・保存・別プロセスでの読み込みを実施した。変更は `upstream-small-trial.patch` として保存済み。

### 短い学習のNaN表示

終局した対戦がまだない時点では、平均リターンの集計対象が空になり、`avg_return=nan` や平均計算の警告が出た。最終モデルの全パラメータが有限値であることは別途確認済み。この集計表示を、直ちに重みが壊れた証拠と解釈しない。

## 8. まだ実施していないことと、次に考える候補

以下は今後の案であり、追加作業の実施決定ではない。

1. **評価を整える**：過去のモデルと固定した相手に対して、先後を入れ替え、学習に使っていないシードで対戦数を増やす。勝敗、異常終了、判断時間を分けて記録する。
2. **学習量を段階的に増やす**：短い実行が動くことは確認できたため、許容稼働時間に合わせてデータ量と改善を測る。初回の数十秒の結果から、強くなるまでの日数を断定しない。
3. **完全な再開機能**：必要なら最適化状態、乱数状態、学習カウンター、設定などを保存する。途中の対戦をリセットして再開する方式と、厳密な続行も区別する。
4. **Jevの補助**：既知の局面でJevの推奨手の質を確かめ、補助なしとの比較実験を行う。API費用・呼び出し回数・遅延も測定対象にする。
5. **別デッキ・新カードへの拡張**：カード効果がエンジンで動くこと、観測・行動の表現、学習データ、対戦性能をそれぞれ確認する。同じテーマ名でも別構築を自動的に対応済みと扱わない。
6. **UI・人との対戦**：今回の検証は画面操作を伴わないローカル実験。対戦画面や助言UIは未整備。公式ゲームやランク戦の自動操作を行った実績はない。

モデルが行動を選ぶときに、相手の非公開手札や山札順が漏れないことは、拡張時にも確認対象。実際の試行では既存実装の `oppo_info=False` を使用したが、包括的な情報漏洩監査を済ませたという意味ではない。
