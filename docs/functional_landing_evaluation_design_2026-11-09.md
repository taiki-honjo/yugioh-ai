# 最終盤面の一致から、使える妨害・手札・後続・実戦成績による評価へ

2026-11-09（日本時間）。設計案。未実装。

目的は、エルフェンノーツ＋キラーチューンのAIが、手本と違う有効な着地点を選べるようにしながら、対戦性能を伸ばすこと。今の盤面判定と採用前の保持検査の両方を設計対象にする。

この資料作成ではコード・設定・モデル・稼働状態を変更せず、学習・対戦も開始していない。確認時の現本番rootは`STOP=now`、`status=stopped`だった。着手時は最新状態を再確認し、別チャットでの開始・停止を勝手に取り消さない。

## 1. 推奨する基本方針

**対戦成績を主な判断材料にし、展開テストは「同じ形の再現」から「能力の維持と大きな退行の検出」へ広げる。**

最初は、学習の勝敗報酬を変えずに評価だけを拡張する。盤面の指標を独自の合計点にして、すぐPPO報酬へ加えることはしない。

評価は次の3層に分ける。

| 層 | 確認する内容 | 用途 |
| --- | --- | --- |
| 正しさ | 合法な行動、公開情報の範囲、エンジン／推論の正常動作 | 実装上の問題と対戦の勝敗を混ぜない |
| 局面の能力 | 使える妨害、残ったリソース、次ターンの展開 | 複数の着地点を認め、何が良く／悪くなったかを説明する |
| 実戦 | 固定相手との先後ペア対戦、別seedでの確認 | 改善が実際の勝敗につながるかを見る |

同じ手札・同じ妨害条件なら、同じ評価版とテスト条件で比べる。相手や妨害条件が違うケースの指標を、そのまま同じ物差しで足し合わせない。

## 2. 現在の実装で厳しい部分

実行中に使われる評価コードは、本番rootの`snapshot/policy-code/`に固定されている。

- `all_opening_witness.py::board_goal()`では、エルフ系の多くは必要カードの包含を判定する。
- JJ系の一部は`ms == set(ending['board'])`で、表側モンスターの**種類集合**を登録例に合わせている。全盤面・枚数・ゾーン・手札の完全一致ではないが、別のモンスターが増えた場合にも不合格になり得る。
- JJ系には、うららを所定の方法で解放し、回収・発動して相手サーチを止める条件もある。
- 一部には大型モンスターの登場順や、特定の手札を残す条件もある。
- `continuous_opening_backend.py::regression_ok()`は、基準で合格したcase_idを1件でも失うと不合格にする。
- `continuous_learning.py::evaluate_candidate()`は、上の不合格で対戦評価へ進まない。

したがって、着地点を数種類増やすだけでは、「未登録の改善が評価前に止められる」問題は残る。

以前の`docs/interruption-landing-evaluation-design-2026-11-09.md`は、主に登録着地点を増やす案で、case_id全維持を残していた。今回の案は、**その保持検査を採用判断へどう使うかまで見直す**点が異なる。

## 3. 盤面をどう見るか

まずは単一の点数を作らず、以下を別々の項目として記録する。

| 項目 | 測りたいこと | 避けたい誤判定 |
| --- | --- | --- |
| 妨害 | 指定した相手の行動を、実際に止める／崩す手段があるか | カードが場にいるだけで、無効化や除去を使えると決める |
| リソース | 自分の手札・場・墓地等に、今後使える札や必要なコストが残るか | 手札枚数だけ多ければ強いと扱う |
| 後続 | 相手ターンを経た後、再展開・回収・攻めへ移れるか | スターターの名前が残っているだけで再展開可能と決める |
| 相手への結果 | 検索阻止、展開抑制、盤面への影響など | 妨害を発動しただけで成功とする |
| 実戦 | 勝敗・先後別成績・相手別成績 | 特定の形や補助点数の増加だけで強化成功とする |

先攻と後攻で目的も分ける。先攻では相手ターンへの対応と後続を重視し、後攻では相手盤面を突破して勝ち切れるかも見る。勝ち切った局面を「守りの盤面を作っていない」として減点しない。現行66件・88件の先攻展開試験を、後攻の突破能力まで測定した結果として扱わず、後攻の機能試験は将来の別枠として設計する。

たとえば「妨害を多く残すが手札が少ない着地」と「妨害は少ないが手札と後続が残る着地」は、別の長所を持つ。どちらがよいかは相手や局面にも依存するため、片方を自動的に失敗へ落とさない。

### 妨害の数え方

カード単位ではなく、効果・発動可能なタイミング・対象・コスト・制限を含めて扱う。

- 効果が使用済み、無効、発動禁止、コスト不足なら、使える妨害とは数えない。
- 1つの効果が複数の種類の行動を止められても、何回も使えることにはしない。
- 複数効果が同じ手札1枚や同じカード名の回数制限を共有するなら、同時に使える手段として重複計上しない。
- 同名カードを複数枚持つ場合も、個体と共有制限を区別する。カード名の集合だけで計算しない。
- 種類の異なる妨害を、すべて同じ「1点」に換算しない。

### 手札と後続の見方

最初は、生の枚数・カード名と、検証できた役割を分けて記録する。

- 使える初動、継続札、回収手段、妨害、コストに使える札。
- 回数制限、必要な対象、使用可能なゾーン、残るEXの札などの条件。
- 手札の同じ1枚を、妨害と後続の両方へ使い切る計算になっていないか。

**通常召喚・セットの回数は診断記録のみ。召喚権温存の加点・合否条件を復活させない。** これはユーザーの現行方針であり、今回の資源評価とは分けて維持する。

## 4. カード名だけでは分からない能力をどう確かめるか

現在のnativeの`benchmark_snapshot()`は、カードのcode・controller・location・sequence・position・level、公開チェーン、合法操作等を返す。一方、全効果について使用済み回数・無効状態・共有コスト・将来の発動可能性を直接判定する十分な情報は揃っていない。

**足りない情報を推測して「使用可能」と断定しない。** 初期版は次の区別を付ける。

- ルールエンジン上の試験で確認できた能力。
- 条件付きで成立する能力。
- 未確認・情報不足。

「未確認」を妨害0として集計し、盤面を弱いと決めない。同時に、未確認の能力を自動採用の根拠にも使わない。

### 二種類の小さな実行試験

1. **能力があるかの試験**：指定した相手行動に対して、合法な応答と必要なコストがあり、実際に機能するかをルールエンジンで確認する。
2. **モデルが使えるかの試験**：同じような状況で、モデル自身が妨害・対象・コストを適切に選べるかを見る。

前者に成功して後者に失敗する場合、盤面に能力はあるが使い方が課題だと分けて記録する。能力判定用の手本・相手の非公開情報・目標を、モデルの入力へ流してはいけない。

相手ターンの指定行動を止めた後、決めた範囲で次の自分のターンまで進め、再始動が合法にできるかを確認する。相手の動き・ドロー・試験範囲・成功条件は事前固定する。あらゆる相手への勝利や最適盤面を保証する試験とは呼ばない。

現在のエンジンに任意時点の保存・復元があるとは仮定しない。必要なら、同じ初手・seed・操作列から再実行して同じ局面を再現する。

## 5. 複数の着地点の登録

初動と妨害の条件ごとに、次の両方を持たせる案とする。

1. 検証済みの具体的な着地点A・B・C。
2. カード名が異なっても、指定した能力・リソース・後続の条件を満たす着地点。

新しい着地点には、合法に到達する正例と、満たしていない負例を付ける。

- 正例は学習区分や評価仕様開発用の初手から作る。validation・最終確認用の操作列を学習へ流用しない。
- 負例には、効果使用済み、コスト不足、対象がない、共有リソースを二重使用、後続を使えない、を含める。
- 位置・表示形式・手札保持・操作順を必須にするのは、それが実際の効果や局面の目的に必要な場合。手本と同じこと自体を目的にしない。
- 未登録の着地点は、新しい発見として記録できるようにする。自動合格・自動的な無価値判定にはしない。

この方法でも全盤面の強さを自動判定する万能な評価器にはならない。試験の条件と、確認できた能力の範囲を明示する。

## 6. JJ系の具体的な見直し例

現在のJJ試験には「指定盤面」「うららを所定の方法で解放」「回収」「相手のサーチへの発動と無効化」が一つの合否に結び付いている。

新しい評価では分けて示す。

| 項目 | 扱い |
| --- | --- |
| JJでうららを解放・回収できるか | 特定の技能の試験として残す |
| 相手サーチを止められるか | 所定のうららルート以外も、合法に達成できれば能力として記録 |
| 次ターンの動きを残せるか | 別の後続試験で確認 |
| 最終的に勝てるか | 対戦評価で確認 |

うららルートを使わなかっただけで、対戦全体の価値を0にしない。一方、そのルートを忘れた事実を「別ルートだから問題なし」と消さない。

同様に、誘発を受けて復旧する技能と、誘発を回避・無効化する技能も分ける。指定妨害が発動しなかった試験は、復旧を実証したことにはしないが、回避できた結果を全体的な失敗と決め付けない。

## 7. 採用判定をどう変えるか

### 現在

基準が解けたcase_idを1件失う → 対戦前に拒否。

### 目指す方向

- 実装異常・情報漏洩・結果の不整合は、別問題として止める。
- 元の着地点に届かなくても、新しい検証済みの能力条件を満たすなら、そのケースを能力維持として評価できるようにする。
- 小さな退行・新しい成功・長所の入れ替わりは、ケース別に見える形で報告し、対戦を調べる道を残す。
- 多くの基本初動や条件群で大きく崩れる場合は、対戦で勝ち越しただけで無条件に自動採用しない。
- 最終的な実戦比較は、先後ペア・固定した相手・別seed確認を使う。当面はミラー。他デッキ評価が完成した後は相手別にも見る。

**「どれだけの低下を許容するか」は、今回まだ数値を決めない。** 任意の重み付き合計点や「失敗3件まで」等を、候補の結果に合わせて設定しない。

初期段階は、旧合否・新しい能力評価・実戦成績を併記する影評価とする。自動採用ルールはその場で切り替えず、計測の妥当性と過去モデルでの傾向を確認してから、今後の実験向けに事前登録する。

旧判定で失敗した候補について、独立した診断対戦を行う場合は別計画とする。影評価の結果を、既存ルールで合格したかのように書き換えない。

過去の16,384判断モデルは、旧保持条件では固定試験1件喪失、対戦では別seedの256戦で170勝86敗となり、総合判断で手動採用した。この履歴は残す。新しい評価版で測る場合は、旧・新モデルの双方を同じ版で測り直し、新版の結果として別に保存する。

## 8. 最初に作る小さな仕様と試験例

最初から全カードの機能辞書を作らず、既知のJJ系と無妨害の基本展開に範囲を絞る。

初期の仕様で確認する例：

1. 元の正解盤面が、新しい評価でも正しく能力を持つと判定される。
2. 異なる着地点が、同じ指定行動を合法に止め、後続も残せる場合に、その能力を認められる。
3. カード名は同じだが、効果使用済み・無効・コスト不足の場合に、能力ありと誤判定しない。
4. 同じリソースが必要な複数効果を、独立して使える妨害として数えない。
5. 特定の回収ルートに失敗しても、別の合法な手段で相手の狙いを止めた場合、その二つを別項目で報告する。
6. 試験が未実装・情報不足なら、未確認を正しく出し、失敗0件に見せたり自動合格にしたりしない。

これらは作成する試験の要件であり、2・5に対応する具体的な別ルートがすでに確認済みだという意味ではない。実際の初手・操作列・ルールエンジンで正例を作る必要がある。

最初の成果物は、評価項目の仕様、少数の正例・負例、現行観測で取得できる情報と不足情報の一覧、旧合否との併記形式まででよい。追加学習を始めず、ここで評価器の設計を確かめる。

## 9. 実装の順番と保持するもの

1. 既存の`own_end`・操作列・最終状態に、新しい評価結果を独立したJSONとして付ける仕様を作る。
2. 使用可能性が実際に確認できる範囲で、小さな能力試験を実装する。静的な場のカード名から全能力を決めない。
3. 旧モデル・採用中モデル・保存済みの退行候補を、仕様開発用の比較として並べる。新しい学習候補を作らない。
4. その結果を見て、自動採用基準の変更案を別途決める。決める前に本番のgateを外さない。
5. 新しい評価版を固定した後、将来の学習・対戦比較へ適用する。

既存の65/66や87/88、手動採用、不合格の記録、元snapshot、モデルの重みは変更しない。

新しい版の仮称は`opening-capability-eval-v1`とする。通常召喚方針のv2、配置補助のv2、既存の展開評価の版と混同しない。

モデルが受け取る観測は引き続き公開・自分の情報のみ。評価用の内部盤面や正解ルートを、学習・推論入力へ混ぜない。

復習の教師データや損失を変更するのは、今回の評価設計とは別の段階とする。新しく有効と認めた別ルートを復習へ追加する場合も、学習区分で合法性を確認してから行う。

## 10. 研究から参考にすること

不完全な代理指標を強く最適化すると、本来の目標とずれる場合があることが研究されている。このため、本件では盤面の独自点数を作ってすぐ学習報酬にする方法を避け、能力の診断と実際の対戦成績を分けて確認する方針を提案する。これはこの遊戯王AIで効果を実証済みの方法という意味ではない。[Goodhart’s Law in Reinforcement Learning](https://arxiv.org/abs/2310.09144)

## Claudeへ渡す設計検討の依頼文

```text
添付の設計案をもとに、最終盤面のカード構成だけでなく、使える妨害・残ったリソース・次ターンの後続・対戦成績で評価する方法を検討してください。

まずは仕様、少数の正例・負例、必要な状態情報と現在不足している情報、旧合否と新評価の併記形式を作ってください。カードが存在するだけで効果を使えると判定せず、合法な発動・コスト・対象・使用回数・共有資源を確認する小さな実行試験を設計してください。盤面に能力があることと、モデルがそれを使えることを分けてください。

JJのうらら解放・回収のような特定の技能は記録として残し、別の有効な着地点や妨害方法も認められる構成にしてください。現在の「既知の1ケースを失うと対戦前に拒否」という使い方を、将来どう変えるかも提案してください。ただし今回は影評価の設計までとし、自動採用基準・勝敗報酬・復習データ・本番コードを変更しないでください。

過去の合否・保持不合格・手動採用・snapshotは保持してください。通常召喚を採点しない方針、情報マスク、版とデータ区分を維持してください。追加学習・対戦の起動・常時運転の停止や再開はせず、未確認の能力や未検証の別ルートは、そのまま未確認として報告してください。
```
