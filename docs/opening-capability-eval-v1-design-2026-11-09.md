# 展開評価 `opening-capability-eval-v1` の設計（影評価）

2026年11月9日（日本時間）。依頼資料：`docs/functional_landing_evaluation_design_2026-11-09.md`。

**設計のみ。** 次のものは変更していない。
- コード、設定、モデル、稼働状態
- 自動採用基準、勝敗報酬、復習データ

学習・対戦の起動、常時運転の停止・再開もしていない。作業時に確認した本番rootは、`STOP=now`、`stopped`、`pending.phase=evaluating` だった。

付属の例：`docs/opening-capability-eval-v1-examples-2026-11-09.json`（正例・負例の仕様）

この文書で「確認済み」と書くのは、コードかエンジンの記録で確かめたことだけである。カードの文章から想定しただけのことは「カード文からの想定（エンジン未確認）」と書く。別の着地点で実際に機能することを確かめたものは、まだない。

## 0. 要点

1. **ケースごとの記録を残す。** 今の保持gateは、ケースごとに合否と手数しか残していない。自分のターン終了時の状態と操作列は捨てている。新しい評価は、まずこれを残すところから始める。
2. **能力は、カード名ではなく実行試験で確かめる。**
   - 決めた相手の行動を発生させ、その時点の自分の合法な応答を列挙する。
   - 応答を実行して、相手の行動を実際に止められたかを確かめる。
   - 調べるのは2種類：盤面に能力があるか（能力試験）と、モデルがそれを使えるか（使用試験）。
3. **判定には5種類の状態を使う。** 確認済み・条件付き・未確認・なし・再現不能。未確認を0として数えず、合格として扱うこともしない。
4. **旧合否は、そのまま併記する。** 当面は影評価で、自動採用基準は変えない。gateの使い方の変更案は第8節に書いた。許す低下の数値は、ここでは決めない。
5. **O1（ルキナのサーチ1回）は、基盤の動作を試すためだけに使う。** 盤面全体の価値や自動採用の根拠にはしない（第11節）。
6. **着地点やカードに、決まった順位や点数を付けない。** トラックメイカーで止める、ザレンへ進む、B2Bへ進むのいずれも状況しだいで有効になりうる。Gやドロールは、直接止めた数とは別の主要な項目として測る（第11節）。

## 1. 現在の判定の棚卸し（コードで確認済み）

実行中の評価コードは、本番rootの `snapshot/policy-code/` にある。

### 1.1 種類ごとの合格条件（`all_opening_witness.py::board_goal()`、`run()`）

| 種類（`kind`） | 自分のターン終了時に求めること | 相手ターン |
| --- | --- | --- |
| `elf` | クリスタルウィング・シンクロ・ドラゴンとフルール・ド・バロネスが表側。パラレリズム（永続魔法）とラプソディア（永続罠）が表側 | 相手は動かない |
| `tune` | トラックメイカー＋リミックスが表側、ジュークジョイントが表側、キラーチューン・シンクロがセット。`mixed` は上に加えて `elf` の盤面も必要 | 相手は動かない |
| `spirit` | ［クリスタルウィングかバロネス］＋トラックメイカー＋リミックスの盤面（`spirit.board_goal`） | `reco-spirit-ash` だけ：ルキナのサーチ1回に対して、リミックスでうららを回収し、うららで無効にする（`cue-spirit` は相手ターンの試験なし） |
| `jj` | 表側モンスターの**種類の集合が、登録した着地の盤面と完全に一致**すること（ザレン＋リミックス、またはトラックメイカー＋リミックス）。指定がある場合は特定の手札を残すこと。ジュークジョイントが表側、シンクロがセット | 同上。加えて、呼んだうららを**ジュークジョイント③のリリースに使う**こと、S素材には使わないこと |
| `rukina` | 既存のルキナ展開。6つのarmのうち5つは、相手がうらら・ヴェーラーで決めた場所を妨害する | 相手は動かない |

`elf` などには、クリスタルウィングを先に場に出すという順序の条件もある（`crystal_first_preference_met`）。

### 1.2 対戦条件

- 相手は**同じデッキ（ミラー）**。相手の初手は、ルキナ・うらら・ヴェーラー・ドロール・Gで固定（`OPP_HAND`）。
- 盤面と初手は `native.set_benchmark_fixture()` で固定し、seedで決まる。

### 1.3 保持gateの扱い

- `continuous_opening_backend.py::regression_ok()`：基準で合格したcase_idを1件でも失うと不合格。
- `continuous_learning.py::evaluate_candidate()`：その場合、対戦評価に進まない。
- `openings_job()`：保存するのは `case_id, family, passed, lua_errors, steps` だけで、終了時の状態（`own_end`）と操作列（`trace`）は捨てている。

### 1.4 直近の運転での影響（事実の記録）

D条件の常時学習（19:16〜19:33）では、5回のうち4回が1〜3件の喪失で対戦前に不合格になった。3回目は、喪失1件と新たな合格1件で、数は基準と同じ65/66だった。これらの候補が本当に弱くなったのかは、現在の記録からは判断できない。

## 2. 評価の構成

### 2.1 層

| 層 | 内容 | 結果の形 |
| --- | --- | --- |
| 正しさ | Luaエラー、合法な行動か、公開情報の監査（`VisibilityAudit`）、手本や目標がモデル入力に入っていないこと、再現（第4.1節） | 合否。問題があれば他の層の結果を無効にする |
| 局面の能力 | 妨害（第2.2節）、リソース（2.3）、後続（2.4）、相手への結果（2.5） | 項目ごとに、状態と根拠を記録する。合計点は作らない |
| 技能の記録 | JJでうららを解放する、リミックスで回収する、クリスタルウィングを先に出す、など既存の個別条件 | した／しない／該当なし。能力の層とは別に記録する |
| 実戦 | 先後を入れ替えたペア対戦、別seedでの確認（既存の評価） | 変更しない |

### 2.2 妨害の数え方

**数える単位は「相手の行動を1つ止めた応答の流れ」で、カードの枚数ではない。**

- **相手の行動は、事前に決めた台本で与える（第4.2節）。** 妨害の能力は、どの相手の行動に対するものかと組で記録する。
  - 例：クリスタルウィング①は、モンスター効果の発動にだけ応答できる（カード文）。
- **応答の流れは、自分の発動の並び。** 例：リミックス②（相手ターンに自身をリリース）→ うららを手札へ → うららで無効。この場合、「リミックス1＋うらら1」ではなく、止めた相手の行動1つと数える。
- **働きは次の項目に分けて、並べて記録する（第11節で改訂）。** どれか1つの数を、盤面全体の強さにはしない。

| 項目 | 意味 | 例 |
| --- | --- | --- |
| 直接阻止 | 台本の相手の行動そのものが機能しなかった。解決後の状態（例：相手の手札に何も加わっていない）で判定する | うららでルキナのサーチを無効 |
| 除去・盤面への影響 | 相手のカードを破壊・バウンス・無効にした。**発動元を除いただけでは、発動した効果を止めたことにしない** | 解決前にルキナを除いても、サーチが通れば直接阻止は0 |
| 継続制限 | 以後の相手の行動を制限した | ドロール（相手がデッキから手札に加えた**後**に適用され、以後の手札追加を制限する） |
| 資源の獲得 | 自分の手札・場・墓地の資源が増えた | Gのドロー、B2B③の回収・特殊召喚 |
| 相手の展開判断の変化 | 相手の行動が変わった（因果の断定には比較の試験が必要） | G |
| 可能にした | 他の応答や展開を可能にした | リミックス②、セットしたキラーチューン・シンクロ |

- **準備と応答を分けて記録する。**
  - 例：相手のドローフェイズにリミックスでうららを回収するのは準備で、後でルキナのサーチにうららを発動するのが応答である。両方の時点とチェーンを記録する。
  - 効果処理の途中に新しく発動する機会がある、とは仮定しない。たとえば、サーチにリミックスをチェーンし、回収したうららを同じサーチへ後から発動する、という正例は置かない。

- 同名カードの1ターン1度の制限、「表側で存在する限り1度」の制限（バロネス②）、コストや対象の有無、すでに使ったかどうかは、エンジンで順に実行して反映する。名前を数えるだけの判定はしない。
- 相手の行動が複数あるときは、許された探索の範囲で、止められた最大数と「探索上限に達したか」を記録する。最適を保証するとは書かない。

### 2.3 リソース

- **生の記録：** 手札・場・墓地・除外・EXデッキに残ったカードのコードと枚数。デッキ残りは、デッキリストから見えている札を引いて評価器側で計算する（順序は記録しない）。
- **役割の表：** 自分のデッキの約20種類について、初動・継続札・回収手段・手札誘発・コスト候補を手で付ける。
  - 表の各行は「カード文から付けた」か「エンジンで確認した」かを区別する。
  - 同じ1枚を、妨害と後続の両方に使い切る計算はしない。
  - 例：手札のうららは、相手ターンに使えば次のターンの初動には使えない。
- **通常召喚・セットの回数は診断記録だけにする。** 召喚権を温存したことへの加点や合否の条件は復活させない。

### 2.4 後続

- 相手が台本どおりに行動してターンを終えた後、自分の次のターン（第3ターン）のメインフェイズ開始時点で調べる。
- **能力：** 初動になる合法な行動（召喚・特殊召喚・発動）があるか。
- **使用：** モデルにNステップ指させて、その時点の盤面とリソースを記録する。
- ドローは、seedと固定の初手で決まり、再実行で再現する。

### 2.5 相手への結果

サーチを阻止した、展開を抑えた、盤面に影響した、などを記録する。妨害を「発動した」だけでは成功にしない。解決後の状態（例：相手の手札の差分）で判定する。

### 2.6 先攻と後攻

- 今回の範囲は先攻だけ（現行の66件・88件はすべて先攻の展開試験）。
- 後攻で相手の盤面を突破する試験は、別の枠として後で設計する。今の結果を、後攻の能力として扱わない。

## 3. 必要な状態情報：今取れるもの、足りないもの

`benchmark_snapshot()`（`runtime/agent/ygoenv/ygoenv/ygopro/ygopro.h`）が返すのは次のものである（コードで確認済み）。

- `to_play`、`message`、`turn_player`、`turn_count`、`phase`、`chain_size`
- `public_chain`［code, player, description］
- `normal_summons`（プレイヤー0の分だけ）、LP
- `cards`［code, controller, location, sequence, position, level］。手札・モンスターゾーン・魔法罠ゾーン・墓地・除外・EXデッキが対象で、**メインデッキは含まない**。
- 判断時点の合法な行動の一覧［act, code, effect（説明番号）, spec, place, position など］

| 情報 | 現在 | 埋め方 | 版への影響 |
| --- | --- | --- | --- |
| 場所・表示形式・レベル | 取れる | — | なし |
| カードの種類・属性・チューナー・S | 取れない（snapshotには無い） | `cards.cdb` を静的に引く | なし |
| デッキの残り | 取れない | デッキリストから、見えている自分の札を引く（評価器だけで使う） | なし |
| その時点で発動できるか | 判断時点の合法な行動だけで分かる | 相手の行動を台本で起こし、自分の応答の合法な行動を調べる（第4節） | なし |
| 効果をこのターンに使ったか | 取れない | 自分の発動は、`trace` の選択（code＋効果の説明番号）から推定する。確定はその時点の合法な行動で行う | なし |
| 「表側で存在する限り1度」を使ったか | 取れない | 同上（`trace` で推定し、合法な行動で確定する） | なし |
| 無効化されているか（ヴェーラーなど） | 取れない | 合法な行動の有無で間接的に確かめる。直接見るにはnativeの拡張が必要 | 拡張すると新しいruntime版 |
| 同名カードの個体の区別 | 取れない（code＋場所＋sequenceだけで、移動すると追えない） | nativeの拡張（カード固有の番号を出す）が必要。拡張までは、同名カードの個体に関わる判定は未確認にする | 新しいruntime版 |
| 現在の攻撃力・守備力 | 取れない | 先攻の初期版では使わない。後攻の試験ではnativeの拡張が必要 | 新しいruntime版 |
| 一時的な特殊召喚の制約（シンクロ・ジュークジョイント③の後はチューナーしか、パラレリズム②の後はSモンスターしかEXから出せない） | 取れない | `trace` の発動から推定する（ターン終了で解ける）。確定は合法な行動で行う | なし |
| 相手の非公開の手札 | snapshotには入っている。モデル入力には無い（`VisibilityAudit` で監査済み） | **評価器だけで使う**（相手のサーチ結果の判定。今の `opponent_search_negated` と同じ方法） | なし |
| 任意の時点の保存・復元 | 無い | 同じ初手・seed・操作の番号の列から再実行し、各段のsnapshotが一致するかで確かめる | なし |
| ケースごとの終了時の状態と操作列 | gateが捨てている | 影評価ではケースごとにJSONで保存する（gateの出力形式は変えない） | 評価の版 |

nativeを拡張すると、本番snapshotの `runtime.json` のハッシュが変わる。拡張する場合は新しい評価版として別に固定し、既存のrootやsnapshotは変更しない。

## 4. 小さな実行試験の設計

### 4.1 再現

- 対象のケースの固定（初手・seed・fixture）と、記録した操作の番号の列（`trace[*].selected.index`）を使って、同じnative版で再実行する。
- 各段で `benchmark_snapshot()` が記録と一致することを確認する。一致しなければ、その試験は**再現不能**とし、失敗とは数えない。
- 分岐は「最初から再実行し、分岐点まで同じ操作を辿り、別の操作を選ぶ」方法で作る。保存・復元の機能は仮定しない。

### 4.2 相手の台本（事前に固定する）

| 台本 | 相手の行動 | 状態 |
| --- | --- | --- |
| O1 ルキナのサーチ | 手札のルキナを①で中央に特殊召喚 → ②（デッキからエルフェンノーツを手札へ） | 今のJJ・spiritの回収試験で使っている（`opponent_steps`） |
| O1×2 | O1を解決した後、手に入れたモンスターで、もう一度モンスター効果を発動する（具体的なカードは、相手の固定手札とデッキで合法に起こせるものを選んで固定する） | 未作成 |
| O-魔法サーチ | 魔法カードによるサーチ（相手の手札fixtureに、ミラーデッキのキラーチューン・シンクロを1枚加える。評価専用のfixture変更） | 未作成 |

- 台本は評価の版と一緒に固定する。候補の結果を見てから変えない。
- 相手が台本にない判断を求められた場合は、今の `passive()` と同じ決まった規則で選ぶ。

### 4.3 能力試験（盤面に能力があるか）

1. 再現した盤面で、台本の相手の行動を発生させる。
2. 自分の判断時点で、合法な応答（`Activate` など）を列挙する。ここで「応答できる候補」が分かる。
3. 候補ごとに、最初から再実行して実行する。その後の選択は決まった規則で選ぶ。対象の選択は最大4通りまで調べる。
4. 相手の行動が**止まったか**を、解決後の状態で判定する。
   - サーチなら、相手の手札にそのカードが増えていない。
   - デッキからの特殊召喚なら、相手の場に出ていない。
   - 場の効果なら、無効または除去された。
5. 台本に相手の行動が複数ある場合は、順に試して、止められた最大数を記録する。分岐数の上限（例：候補8×対象4×行動3）に達したかどうかも記録する。
6. **合法な発動の候補があることは、止められる証拠ではない。** 実行して、解決後の結果まで確かめる。
7. **「なし」を出す条件を限る。** 応答の流れが1つ見つかれば、その能力がある証拠になる。一方、調べた範囲で見つからなかっただけでは「なし」にしない。調べ切っていない、上限に達した、再現できない場合は、未確認か再現不能とする。「なし」には、何について、どの範囲で不可能と確かめたかを書く。
8. 1つの相手の行動に対する複数の対処候補を、独立した妨害回数として足さない。連続して何回止められるかは、共有の資源と使用回数の制限を引き継いだ、別の試験で測る。

### 4.4 使用試験（モデルがそれを使えるか）

- 同じ再現と台本で、自分側の判断をモデルが行う。今の `run()` も、相手ターンの自分側の判断はモデルが行っている。
- 結果は次のように分類する。
  - 正しく使った
  - 使えたのに使わなかった
  - 対象・コスト・順序が違った
  - そもそも使えなかった（能力試験で「なし」）
- 能力試験で使った手本・相手の非公開情報・目標は、モデルの入力に入れない（`VisibilityAudit` と `model_received_goals_or_plans=False` を維持する）。

### 4.5 後続試験

- 台本の後、相手はターンを終える。自分の第3ターンのメインフェイズ開始時点で、初動になる合法な行動を記録する（能力）。
- モデルにNステップ指させて、盤面とリソースを記録する（使用）。
- 「次のターンに勝てる」「最適な盤面になる」は保証しない。範囲は「決めた条件で、合法に再始動できるか」である。

### 4.6 状態の5区分

| 状態 | 意味 |
| --- | --- |
| 確認済み | この試験の範囲で、エンジン上で実行して成立した |
| 条件付き | 成立には条件が必要で、その条件はこの局面で満たされていない。例：ザレン②は、チェーンに乗った効果にしか応答できない（カード文） |
| 未確認 | 試験が無い、情報が不足、探索の上限に達した |
| なし | 試験を行い、合法な応答が無かった、または止められなかった |
| 再現不能 | 再実行がsnapshotと一致しなかった |

## 6. JJ系の分け方

| 今の合否の要素 | 新しい扱い |
| --- | --- |
| 表側モンスターの種類の集合が、登録した着地と一致 | 「登録した着地A／Bに到達」として記録する（技能・再現の記録）。能力の判定には使わない |
| 指定した手札を残す | リソースの記録（2.3）と後続試験（2.4）で評価する |
| 呼んだうららをジュークジョイント③のリリースに使い、S素材にしない | 技能「JJ解放」。する／しないを記録する。しなかったことを「別ルートだから問題ない」として消さない |
| リミックス②でうららを回収 | 技能「回収」。妨害の応答の流れとしても記録する |
| うららでルキナのサーチを無効にした | O1に対する妨害（止めた）。うらら以外の合法な手段で止めた場合も、能力として記録する |

誘発を受けて立て直す技能と、誘発を避ける・無効にする技能も分ける。

- 指定した妨害が発動しなかった試験は、立て直しを実証したとはしない。
- 妨害を避けられた結果を、全体の失敗と決め付けない。

**B2B（ローカルDBのカード文）**
- ①：相手の場のモンスターのレベルを上げる。
- ②：自分のチューナーの2回攻撃。
- ③：相手がモンスター効果を発動した時、レベル10以外の自分の墓地・除外のチューナー1体を手札に加えるか特殊召喚する。その後、S召喚できる（1ターンに2度まで）。

O1（ルキナ②はモンスター効果）は③の発動条件に当てはまるが、③は直接阻止ではなく、資源の獲得とS展開である。記録する項目は次のとおり。
- 条件・対象・使用回数・残る資源
- 回収と特殊召喚のどちらを選び、何につなげたか
- 追加で出たSモンスターが、いつ何をできるか
- 次の攻撃での突破・決着

効果処理の途中で出したカードが、進行中のチェーンに割り込めるとは仮定しない。タイミングと使えるかどうかは、エンジンで確認する。

### 11.3 Gとドロール

直接の無効、継続制限、資源の獲得、展開の誘導は、どれも主要な働きとして並べて記録する（2.2の表）。「直接止めた数が0だから価値も0」としない。

| 対象 | 主に記録する項目 | 測る試験 |
| --- | --- | --- |
| 増殖するG | 効果が通ったか、実際の追加ドロー、引いたカードの働き、相手の特殊召喚・展開の変化、その後の勝敗 | (1) 固定の台本で相手が展開を続け、実際のドローと資源を確認する。(2) 相手AIが選ぶ試験で、同じ初手からGを使う・使わないを比べる。相手がたまたま止まった1例で因果を断定しない |
| ドロール | 効果が通ったか、以後の手札追加の制限、相手の後続展開の変化、自分側への制約、その後の勝敗 | 最初の手札追加の後にさらに手札追加を行う、複数行動の台本。制限がなければ合法だった後続の行動が、制限で実行できない・機能しないことを記録する。相手が特定の行動を選ばなかっただけで、制限の成果とはしない |
| 直接の無効・除去 | 対象の行動への実際の結果、使ったコスト、残る使用回数 | O1ほか。直接止めた数だけを総合的な強さにしない |

**ドローの区別**
- Gによるドローと、他の効果で得たカードを区別する。区別できない場合は、推定または未確認と表示する。
- カードの枚数を増やすこと自体を、学習報酬にはしない。

**Gとドロールの相互作用**
- ドロールが適用されている間は、Gによるドローも行えない。Gが先に適用されていても同じである（公式Q&A、補足資料のリンク）。
- そのため、「G＋ドロール」の働きを、それぞれの最大の働きの足し算にしない。使う順番、すでに得たドロー、以後の制限の利益、自分側で失う手段を分けて記録する。

### 11.4 O1の位置付け

O1は、記録の保存・再現・発動と解決の判定を作るための**基盤試験**である。次のものを代表しない。
- ザレンの条件に合うチェーンへの対応
- B2Bからの資源回復・S展開・攻撃
- Gの資源獲得と相手の判断への影響
- ドロールによる後続の行動の制限

O1の結果だけで、これらの盤面やカードを弱いと判定しない。これらを測らないまま、能力評価を本番の採用基準に結び付けない。
