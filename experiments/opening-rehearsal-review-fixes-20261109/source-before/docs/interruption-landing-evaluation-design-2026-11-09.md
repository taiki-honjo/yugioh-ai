# 変更B（別段階）設計：妨害後の複数の着地点を受け入れる評価拡張

2026年11月9日（日本時間）。**設計のみ。評価コード・合格条件・閾値は今回一切変更していません。**

変更A（展開復習の補助損失）の比較は、すべて現行の評価（以下「評価v1」）で行いました。保持損失の効果と採点変更の効果を同時に比較しないため、この拡張は変更Aの結論が出た後に、別の実験rootで行います。

## 1. 現行（評価v1）の扱い

| 項目 | 現行の実装（snapshot/policy-code） |
| --- | --- |
| 自由実行の入口 | `continuous_opening_backend.openings_job()` → `all_opening_witness.run(case, policy)` |
| ルキナ系6分岐 | `rukina_recovery_witness.goal()`。分岐ごとに1つの盤面述語。うらら/ヴェーラーが実際に使われ解決したこと（`interruption.used and resolved`、`ash_parallelism`は`countered`）を要求 |
| エルフェンノーツ系 | `board_goal()`：クリスタルウィング＋バロネス＋パラレルエルフ＋ラプソディア |
| JJ系 | `accepted_endings`（同じ初手の複数の終盤）をすでに許容 |
| スピリット系 | クリスタルウィング版とバロネス版の両方を許容 |
| 召喚権 | 記録のみ。合否・加点・減点に使わない |
| 採用前の保持 | 基準モデルが解けた case_id をすべて維持（`regression_ok`）。件数一致でも入れ替わりは不合格 |

未知の妨害から実現可能な最善盤面を求める仕組みはありません。この設計でも作りません。

## 2. 評価の3層

| 層 | 対象 | 合否への影響 |
| --- | --- | --- |
| L1 無妨害の基本展開 | 既存の `pass` 系・エルフ系・チューン系 | 既存の着地点と保持基準をそのまま使う |
| L2 指定された単発妨害 | 既存の6分岐など、所定のタイミングで所定の妨害が**実際に発動・解決**した場合 | 条件ごとに登録・検証済みの**複数**の着地点のいずれかで合格 |
| L3 未登録の妨害・複数妨害 | 新しい妨害の種類やタイミング、2枚以上 | **合否に入れない**。診断として別集計し「要確認」に分類 |

「妨害を受けたら何でも合格」にはしません。L2の着地点は条件（家族・妨害の種類・対象・必要な初手カード）ごとに個別に定義します。

## 3. 着地点の登録形式（案）

`evaluation/opening-eval-v2/landing_points.json`（新設予定・版付き）

```json
{
  "evaluation_version": "opening-eval-v2",
  "conditions": [{
    "eval_family": "rukina-ash_rukina",
    "interruption": {"card": "ash", "target": "rukina", "must_resolve": true},
    "requires_in_opening_hand": ["level-1 tuner"],
    "landing_points": [{
      "id": "strelitzia-center-rukina-side",
      "board": {"monsters": [{"code": "STREL", "zone": "center"}, {"code": "RUK", "zone": "side"}]},
      "retained": {},
      "capabilities": ["記録のみ：残った妨害・次ターンの展開手段"],
      "positive_witness": ["学習区分の初手から作った合法な再現手順とハッシュ"],
      "negative_witnesses": ["1枚足りない盤面", "効果が使えない状態", "妨害が未解決"]
    }]
  }]
}
```

- **正例**：ルールエンジン上で合法に再現できた操作列（学習区分の初手から生成）。到達できる証拠であって、強さの証拠ではありません。
- **負例**：届いていない盤面、効果を使えない状態（例：無効化効果を使用済み）、妨害が実際には解決していない、の各例で不合格になることを確認します。
- **能力の記録**：妨害として使える効果、維持したリソース、次ターンの動きを記録します。カード枚数やATKの単純な合計を強さの正解にしません。これらを学習報酬へ足すことは別の検証を要する変更として扱い、この段階では行いません。

## 4. 判定の出力（案）

1件ごとに次を**別々に**残します。既存の不合格を隠したり失敗件数から消したりしません。

| フィールド | 意味 |
| --- | --- |
| `v1_passed` | 評価v1の判定（そのまま保持） |
| `v2_passed` | 評価v2の判定 |
| `interruption_verified` | 指定妨害が所定の状況で実際に発動・解決したか |
| `landing_point_id` | 一致した登録着地点（なければ null） |
| `status` | `pass` / `fail` / `needs_review`（L3、または未登録の妥協盤面） |
| `trace` / `own_end` / `final` | 操作列と終局状態（要確認の後日審査用） |

`needs_review` は自動採用に使いません。人が確認して正例・負例を付けて登録した後、**新しい版**として扱います。

## 5. 復旧の試験と回避の試験を分ける

既存のL2試験は「妨害が実際に解決したこと」を要求します。妨害を回避した・踏ませた動きはこの試験では不成立になり得ます。

- 復旧試験：妨害が解決した後の着地点を評価（現行の意図）。
- 回避試験：妨害を回避・誘発させる選択を別の家族として評価。回避して妨害が解決しなかった場合は、復旧試験上「不適用」と記録し、失敗と混ぜません。

## 6. 版の管理と保持検査

1. 評価ルールに `evaluation_version` を付け、`openings_job` の結果JSONと `regression_ok` の比較対象に記録します。**版が異なる結果同士は比較しません。**
2. 版を切り替えるときは、採用モデルと新候補を**同じ新版**で測り直します。65/66・86/88 は評価v1の記録として残し、新版の結果として書き換えません。
3. 「基準モデルが解けた case_id をすべて維持」という採用前検査は維持します。複数の着地点を認めることと、この保護を外すことを混同しません。
4. 同じ候補を通すためにその場で閾値・目標を緩めません。条件変更の検証（正例・負例）と、候補比較を別の実行に分けます。
5. 新しいルートを学習へ足す場合は学習区分の初手から生成します。validationで見つけた成功操作列をtrainへ流用しません。holdoutは今後も反復選別に使わず、最終確認用には新しい固定試験を別途用意します。

## 7. 実装時の検証項目

- 正例：登録した各着地点が合法な再現例で合格する。
- 負例：1枚足りない盤面、効果使用済み、妨害未解決、妨害が別対象、で不合格になる。
- 指定妨害の発動・解決の判定（`used`/`resolved`/`countered`）が既存と一致する。
- L3の結果は `needs_review` になり、`passed` に数えない。
- v1の結果ファイル・ハッシュが変わらない。v2の結果は版付きの別ファイルに出る。
- 採用モデルの v1 と v2 の差（新たに合格・新たに不合格）をcase_id単位で列挙する。

## 8. 変更Aとの順序

変更Aの比較（`experiments/opening-rehearsal-ab-20261109/`）は評価v1のみで判定しました。変更Bを実装する際は、変更Aの学習条件を固定したまま、採点の変更だけを別rootで比較します。
